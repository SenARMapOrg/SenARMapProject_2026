# 鳳祭の案内人数集計（設計メモ・未着手）

> 2026-10-01 時点の方針メモ。実装はまだしていない。今の集計に使っている Rails アプリがこのリポジトリ・この開発機に無いため、
> Rails 側を触れる環境で再開する。

## 目的

鳳祭（イベントモード）で、**どの案内係が何人を案内したか**を集計する。

## 今の仕組みと問題

- 流れ: 案内係ごとの QR → **Rails のリダイレクト数カウンター** → IKU NAVI（`navi/?event=1`）
- Rails が「リダイレクトのリクエストが来た回数」を数えているため、**QRを読み込んだ瞬間と実際に開いた瞬間の2回数えられる**ことがある
- 想定される原因（サーバーに来るリクエストは本人の閲覧だけではない）:
  - QR リーダー・LINE・Slack などのリンクプレビュー（User-Agent に `Line` / `facebookexternalhit` / `Slackbot` など）
  - ブラウザの先読み（`Sec-Purpose: prefetch` / `Purpose: prefetch` ヘッダ）
  - アプリ内ブラウザ →「Safari で開く」での開き直し
  - HEAD リクエスト

## 集計したいもの（決定事項）

1. **QRを読み込んだ人数**（今の「利用者数」に相当）
2. **実際にルート検索まで進んだ人数**
3. **どこからどこまでを検索したか**（出発地・目的地。イベント名・教室名）

## 方針（案）

サーバーでリダイレクトを数えるのをやめ、**IKU NAVI のページが実際に開いたあとに、ページ内の JavaScript から記録を送る**。

- QR は案内係ごとに `https://iku-navi.net/navi/?event=1&ref=<案内係コード>` を直接指す
  - `ref` はランダムな短いコード。名前などの個人情報は URL に入れない（コード ↔ 案内係の対応表はサーバー側だけに持つ）
- ナビ画面（`programs/html/navi/script/`）で次のタイミングに `navigator.sendBeacon` で送る
  - **到着**: ページを表示したとき。`document.prerendering` が true の間は送らない（先読みを数えない）
  - **ルート検索**: `doSearch()`（`route.js`）・設備検索で、経路の取得に成功したとき。出発地・目的地（`from_event` / `to_event` / 教室名・号館）を付ける
- **端末ごとの重複を除く**: 初回にランダムな端末IDを作って localStorage に保存し、一緒に送る。
  集計時は「案内係 × 端末ID × 日付」で1人と数える（到着はユニーク制約、検索は全件残して集計で数える）
- `ref` はページ内で sessionStorage に持っておき、同じタブで検索したときにも付ける
- 保存先の候補: Cloudflare（Pages Functions か Workers）＋ D1。時間割共有と同じ構成なので、案内係ごとの人数を見る画面も
  時間割共有の管理画面（`/admin`）と同じ作り（許可したメールアドレスだけ・閲覧記録あり）で作れる
- Rails をしばらく残す場合の暫定対策: HEAD・プレビュー用 User-Agent・`Sec-Purpose`/`Purpose: prefetch` を数えない、
  `Cache-Control: no-store`、Cookie で同じ人の数分以内の再アクセスを数えない

## 限界・決めること

- 1台のスマホを数人で見る場合は1人になる（数えられるのは「案内した端末の数」）
- ブラウザを乗り換えると localStorage が別になるため、その分は別の人として数えられることがある
- 検索内容（出発地・目的地）の記録は個人を特定しない範囲にとどめる。端末IDはランダムで、個人情報とは結びつけない。
  記録していることをイベントページなどで一言案内するか決める
- 未定: 実装時期、Rails のカウンターから切り替えるか併用するか、記録の保存期間
