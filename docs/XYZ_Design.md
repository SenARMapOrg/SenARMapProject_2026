# キャンパスマップARプロジェクト：データ構造設計仕様書

## 1. 座標系定義 (Coordinate System)

各建物のデータは**建物ローカル座標系**で入力し、後述の変換パラメータによってグローバル座標に統合します。

* **単位**: メートル（小数点第1位まで保持、10cm単位の精度）。
* **軸の向き**（各建物共通）:
    * **X軸**: 建物基準で「山を登る方向（斜面の上方）」をプラスとする。
    * **Y軸**: X軸のプラス方向に対して右向きをプラスとする。
    * **Z軸**: 高さ（垂直方向）をプラスとする。
* **原点**: 建物ごとに任意に設定してよい（変換パラメータで吸収する）。10号館は正面エントランス（node ID: 1）を原点とする。

## 2. データディレクトリ構成

```
data/
├── {building_id}_bldg/      # 建物ごとのディレクトリ（例: 10_bldg/）
│   ├── node.csv             # ノードデータ（建物ローカル座標）
│   └── edge.csv             # エッジデータ
├── global_node.csv          # 屋外ノード ＋ アンカー参照座標（グローバル座標）
├── global_edge.csv          # 屋外エッジ（屋外ノード間・建物との接続）
├── connect_edge.csv         # （任意・存在すれば読込）建物間直接接続エッジ（グローバルIDで記述、屋外ノード不要の場合）
├── edge_image.csv           # エッジ→AR経路画像のマッピング（CDNファイル名）
├── cafeteria_edge.csv       # 食堂情報（name / building / display_name）
├── buildings.json           # 各建物の座標変換パラメータ（手動設定・微調整用）
├── anchors.csv              # アンカーノード対応表（自動変換パラメータ計算用）
└── name.csv / building_name.csv / ignore.csv / event.csv   # 表示名DB・イベントモード（`docs/NameDB_EventMode.md` 参照）
```

新しい建物を追加する場合は `{building_id}_bldg/` ディレクトリを作り、その中に `node.csv` と `edge.csv` を置くだけで自動的に読み込まれます。`connect_edge.csv` は2026年9月時点で `data/` に存在しない（ファイルが無い場合は単に読み込みをスキップする仕様）。現状の建物間接続はすべて `global_node.csv` + `global_edge.csv` + `anchors.csv`（アンカー方式）経由。

## 3. 点データ仕様 (`{building_id}_bldg/node.csv`)

ノード（地点）を定義します。入口、階段前、分岐点などに配置します。

| カラム名 | データ型 | 説明 | 備考 |
| :--- | :--- | :--- | :--- |
| `id` | Integer | 建物内で一意な識別子 | 1始まりの連番を推奨 |
| `x` | Float | X座標 (10cm単位) | 建物ローカル座標 |
| `y` | Float | Y座標 (10cm単位) | 建物ローカル座標 |
| `z` | Float | Z座標 (10cm単位) | 高さ（例: 1階=5.0, 2階=10.0） |
| `building` | Integer | 建物ID | ディレクトリ名の数値部分（例: `10`） |
| `floor` | Integer | 階数 | 数値のみ (例: 1, 2) |
| `type` | Integer | 地点の属性 | 1: 通常ノード, 2: 出入り口（建物外と接続する地点） |
| `svg_x` | Float | 任意列。屋内SVGフロアマップ上でのX座標 | `programs/SVG_Pointer` や `Map_Editor` で取得・編集する。列自体が無い建物は屋内SVGマップ・SVGナビが機能しない |
| `svg_y` | Float | 任意列。屋内SVGフロアマップ上でのY座標 | 同上 |

`svg_x`/`svg_y` は2026年9月時点で **10号館の `node.csv` にのみ存在**する任意列。列が無い建物は `x/y/z` による3D表示・経路探索は問題なく動作するが、`programs/html/svg/{building}_{floor}F.svg` を使った屋内フロアマップ表示ができない。

**入力例:**
```csv
id,x,y,z,building,floor,type,svg_x,svg_y
1,0.0,0.0,5.0,10,1,2,493,1630.1
2,5.0,0.0,5.0,10,1,1,493,1530
3,5.0,3.0,5.0,10,1,1,540,1530
```

## 4. 線データ仕様 (`{building_id}_bldg/edge.csv`)

エッジ（経路）を定義します。点と点を結び、教室情報や移動コストを保持します。

| カラム名 | データ型 | 説明 | 備考 |
| :--- | :--- | :--- | :--- |
| `id` | Integer | 建物内で一意な識別子 | |
| `name` | String | 教室名・施設名 | 複数ある場合は `;` 区切り (例: `101A;101B`)。なければ空欄 |
| `from` | Integer | 開始ノードID | 同建物の `node.csv` の `id` に対応 |
| `to` | Integer | 終了ノードID | 同建物の `node.csv` の `id` に対応 |
| `building` | Integer | 建物ID | ノードデータに準拠 |
| `floor` | Integer | 階数 | そのエッジが属する階（階をまたぐ場合は低い方） |
| `weight` | Float | 経路探索用の重み | 1: 平坦な通路, 5: 階段, 任意: 坂道 |
| `length` | Float | 物理的な距離 | メートル単位 |
| `type` | Integer | 経路の種別 | 下表参照 |
| `right` | String | 任意列。`from→to` の進行方向を向いたとき**右側**にある教室名 | `;` 区切り。無ければ空文字。`name` 列とは独立した列で、`name` のリストは並び順が正しいとは限らないため、進行方向の右側・左側にある教室名をそれぞれ正しい順序で入れる想定 |
| `left` | String | 任意列。`from→to` の進行方向を向いたとき**左側**にある教室名 | 同上 |

`right`/`left` は2026年9月時点でどの建物の `edge.csv` にも実データは入っていない（列自体が無くても空文字として動作する）。将来、音声案内（naviの右左折案内）などで「左手に◯◯教室があります」のような案内を出す際に使う想定の列。

CSVには `from`→`to` 片方向の値しか記述しないが、経路探索でその区間を逆向き（`to`→`from`）に通る場合、`programs/3D_Graph/app.py` の `build_graph` がグラフに逆方向のエッジを追加する際に `right`/`left` を自動的に入れ替える。そのため CSV編集者は常に「CSVの `from`→`to` 方向を向いたときの右左」だけを意識すればよく、API（`path_edges`）から返る値は経路の実際の進行方向を基準にした値になる。

### エッジ種別 (`type`)

| 値 | 種別 | 双方向 | 備考 |
| :--- | :--- | :---: | :--- |
| `1` | 通常通路 | ✓ | 廊下・屋外通路など |
| `2` | 階段 | ✓ | |
| `3` | エスカレータ | ✓ | 上下どちらにも使える（例: 止まっているエスカレータ） |
| `4` | エレベータ (EV) | ✓ | アプリ側で使用可否を切り替え可能 |
| `5` | 上りエスカレータ | **一方向** | **低いz→高いz** 方向のみ通行可。CSVの `from/to` の向きに関わらず z座標で自動補正される |
| `6` | 下りエスカレータ | **一方向** | **高いz→低いz** 方向のみ通行可。同上 |
| `7` | 入口（屋内外接続） | ✓ | `anchors.csv` から自動生成される。通過コストに入口ペナルティ（+50）が加算される（§8参照） |

**入力例（`right`/`left` は付けなくてもよい任意列）:**
```csv
id,name,from,to,building,floor,weight,length,type,right,left
1,,1,2,10,1,1,5.0,1,,
2,10101,2,3,10,1,1,3.0,1,101;102,103
3,,10,20,10,1,5,8.5,2,,
4,,30,40,10,4,1,22.2,5,,
```

## 5. 屋外ノード (`global_node.csv`)

屋外の経路上に置く地点（建物入口前の分岐点・屋外通路の中継点など）を定義します。**グローバル座標で直接記述**します（建物ローカル座標ではありません）。

このファイルは**アンカー方式の座標変換**でも参照されます（§7参照）。

| カラム名 | データ型 | 説明 | 備考 |
| :--- | :--- | :--- | :--- |
| `id` | Integer | 屋外ノードの識別子 | 1始まりの連番を推奨 |
| `x` | Float | グローバルX座標 (m) | |
| `y` | Float | グローバルY座標 (m) | |
| `z` | Float | グローバルZ座標 (m) | |
| `lat` | Float | 緯度（WGS84） | GPS ナビ・屋外 AR で使用 |
| `lng` | Float | 経度（WGS84） | 同上 |
| `floor` | Integer | 階数 | 現行データは `0` を使用（屋外判定は `building=0` で行うため値は探索に影響しない） |
| `type` | Integer | 地点の属性 | 1: 通常ノード, 2: 出入り口 |
| `name` | String | ノード名 | 任意。省略可 |

**内部処理**: 読み込み時に `id` へ `9,000,000` のオフセットが自動付与されます（建物ノードIDとの衝突防止）。3D ビューでは緑色の四角マーカーで表示されます。

**入力例:**
```csv
id,x,y,z,lat,lng,floor,type,name
1,0.0,0.0,0.0,35.61084,139.55369,0,2,10号館前
2,30.0,5.0,0.0,35.61087,139.55393,0,1,
3,60.0,0.0,0.0,35.61090,139.55420,0,2,1号館前
```

## 6. 屋外エッジ (`global_edge.csv`)

屋外ノード同士、または屋外ノードと建物ノードを繋ぐエッジを定義します。

| カラム名 | データ型 | 説明 | 備考 |
| :--- | :--- | :--- | :--- |
| `id` | Integer | 一意な識別子 | |
| `name` | String | 表示名 | なければ空欄 |
| `from` | Integer | 開始ノードID | 屋外ノードは `global_node.csv` の `id`、建物ノードはグローバルID |
| `to` | Integer | 終了ノードID | 同上 |
| `floor` | Integer | 階数 | 屋外は `1` を使用 |
| `weight` | Float | 重み | 1: 平坦, 任意: 坂道 |
| `length` | Float | 距離 (m) | |
| `type` | Integer | 種別 | `1`: 屋外通路 など |

### `from/to` のID指定方法

| 接続先 | 書き方 | 例 |
| :--- | :--- | :--- |
| 屋外ノード | `global_node.csv` の `id` をそのまま記述 | `1`（屋外ノード1番） |
| 建物ノード | `building_id × 100,000 + ローカルID` | `1000005`（建物10・ノード5） |

システムが屋外ノードIDを自動的に `+9,000,000` に変換するため、ユーザーは元の小さいIDで記述できます。

**入力例（屋外ノード1 ↔ 建物10のノード5 を繋ぐ場合）:**
```csv
id,name,from,to,floor,weight,length,type
1,,1,1000005,1,1,12.0,1
2,,1,2,1,1,30.0,1
3,,2,3,1,1,30.0,1
4,,3,1000003,1,1,8.0,1
```

## 7. 建物間直接接続 (`connect_edge.csv`)

屋外中継ノードが不要で、**建物の出入り口ノード同士を直接繋ぐだけ**でよい場合に使用します。`from/to` にはグローバルIDを記述します。

> **注意: このファイルはエッジのみ追加できます。**  
> 屋外に中継ノードが必要な場合は `global_node.csv` + `global_edge.csv` を使ってください。

```
グローバルID = building_id × 100,000 + ローカルID
例: 建物10のノードID 1 → 1,000,001
```

| カラム名 | データ型 | 説明 | 備考 |
| :--- | :--- | :--- | :--- |
| `id` | Integer | 一意な識別子 | 他のエッジIDと重複しないよう大きい値を推奨（例: 900001〜） |
| `name` | String | 表示名 | なければ空欄 |
| `from` | Integer | 開始ノードのグローバルID | |
| `to` | Integer | 終了ノードのグローバルID | |
| `building` | Integer | 代表建物ID | |
| `floor` | Integer | 階数 | |
| `weight` | Float | 重み | |
| `length` | Float | 距離 (m) | |
| `type` | Integer | 種別 | |

## 8. 座標変換パラメータ

各建物のローカル座標をグローバル座標に変換するには、以下の2通りの方法があります。**アンカー方式が推奨**です。

### 方法A: アンカー方式（自動計算・推奨）

`global_node.csv` 上のノードを「アンカー点」として使用し、建物ローカルIDとの対応を `anchors.csv` に記述することで変換パラメータが自動計算されます。

#### アンカー点数と自動計算の範囲

| アンカー点数 | 自動計算される内容 | 備考 |
| :---: | :--- | :--- |
| **2点以上** | 平行移動（tx, ty, tz）＋ Z軸回転（rot_deg）を完全自動計算 | 推奨 |
| **1点のみ** | 平行移動（tx, ty, tz）のみ自動計算 | 回転は `buildings.json` の `rot_deg` を使用（なければ 0°） |

#### `anchors.csv` — 建物ローカルIDとグローバルノードIDの対応

| カラム名 | データ型 | 説明 |
| :--- | :--- | :--- |
| `building` | Integer | 建物ID |
| `local_node_id` | Integer | 建物内のノードID（`node.csv` の `id`） |
| `global_node_id` | Integer | `global_node.csv` の `id` |

```csv
building,local_node_id,global_node_id
10,1,1
10,50,3
```

### 方法B: 手動設定 (`buildings.json`)

アンカーが用意できない場合、または微調整を行う場合に `buildings.json` を使用します。**アンカー方式が存在する建物でも、`rot_deg`（1点アンカー時）と `tz_offset`（常時）は `buildings.json` から読まれます。**

```json
{
  "10": { "tx": 0.0, "ty": 0.0, "tz": 0.0, "rot_deg": 0.0, "tz_offset": 0.0 },
  "1":  { "tx": 50.0, "ty": 20.0, "tz": 0.0, "rot_deg": 15.0 }
}
```

| キー | 説明 | アンカーとの関係 |
| :--- | :--- | :--- |
| `tx`, `ty` | X・Y方向の平行移動量 (m) | アンカーがある場合は上書きされる |
| `tz` | Z方向（高さ）の基準オフセット (m) | アンカーがある場合は上書きされる |
| `rot_deg` | Z軸周りの回転角（度）。反時計回りをプラス | 2点以上アンカーがある場合は上書きされる。1点アンカー時はここの値が使われる |
| `tz_offset` | 高さの追加オフセット (m) | アンカー計算後に**加算**される。微調整用 |

`buildings.json` の編集は手動で行い、反映にはアプリの再起動（キャッシュ再構築）が必要です。

#### アンカーによる接続エッジの自動生成

`anchors.csv` の対応 1 行ごとに、建物ローカルノード ↔ 屋外ノードを繋ぐ **type 7（入口）** のエッジが自動生成されます。type 7 エッジには入口通過ペナルティ（`app.py` の `ENTRANCE_PENALTY = 50.0`）がコストに加算され、建物を通り抜けるだけのルートが選ばれにくくなっています。

## 9. 新規建物の追加手順

1. `data/{building_id}_bldg/` ディレクトリを作成する
2. `node.csv`・`edge.csv` を上記仕様に従って作成する
3. 座標変換パラメータを設定する
   - **2点アンカー（推奨）**: `global_node.csv` にアンカー点を追記 → `anchors.csv` に対応を記述 → 自動計算
   - **1点アンカー**: 上記に加え `buildings.json` に `rot_deg` を設定（回転のみ手動）
   - **手動**: `buildings.json` に `tx`, `ty`, `tz`, `rot_deg` をすべて記述
4. 他建物や屋外と接続する場合:
   - 屋外ノードが必要 → `global_node.csv` に追記 → `global_edge.csv` で接続
   - 直接接続のみ → `connect_edge.csv` にグローバルIDで記述

## 10. 運用ルール・仕様

* **ID の一意性**: 建物内では `node.csv`・`edge.csv` それぞれで ID が重複しないようにする。建物をまたいだ一意性はグローバルIDで担保される。
* **屋外ノードID**: `global_node.csv` の `id` はシステム内部で `9,000,000` を加算したIDとして管理される。`global_edge.csv` への記述は元の小さいIDで行う。
* **重み (`weight`)**: ナビゲーション時の優先度として使用。階段回避などの設定に影響する。
* **エレベータ (`type: 4`)**: アプリ側で「エレベータを使用するか」を切り替え可能。`use_elevator=0` のパラメータで経路探索から除外できる。
* **一方向エスカレータ (`type: 5/6`)**: `from/to` の向きに関わらず、システムが z座標を参照して正しい方向に自動補正する。type 5 は必ず低い階→高い階、type 6 は必ず高い階→低い階のみ通行可となる。
* **`right`/`left`（進行方向の左右にある教室名）**: `from→to` を向いた進行方向を基準に記述する。`name` 列は複数教室を `;` 区切りで並べるだけで順序を保証しないため、左右を正しく案内したい場合は `right`/`left` を別途埋める。列が無い建物・行は空文字として扱われ、経路探索や他機能には影響しない。
* **スプレッドシートからの更新**: データはスプレッドシートからスクリプト経由でGitHub Pushする運用とする（`NonFunctionalRequirements.md` 参照）。
