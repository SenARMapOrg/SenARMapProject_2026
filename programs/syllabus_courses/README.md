# syllabus_courses — 専修大学シラバスサイト スクレイパー

`programs/timetables/`（時間割共有アプリ）向けに、**科目名オートコンプリート／曜日・時限の参考データ**
を作るためのスクレイパー。専修大学のWebシラバス（講義要項）検索サイトから開講科目一覧を収集する。

## これは何のためのデータか（重要・必ず読むこと）

このツールが集めるのは大学のシラバスサイトに公開されている「開講科目情報」（科目名・曜日・時限・学期・
担当教員）であり、**特定の学生が実際にその授業を履修しているかどうかは一切分からない**。
シラバスサイトは「この科目はこの曜日・時限に開講される予定です」という開講情報を公開しているだけで、
誰が履修登録しているかという名簿情報ではない。

`output/courses.json` は「時間割を手入力するときに科目名を選びやすくする」「曜日・時限の候補を出す」
ための **参考データセット** として使うことを想定している。これを使って「この学生はこの授業を取っている
はず」といった個人の履修状況の推測・表示をする機能には**絶対に使わないこと**。timetables アプリ側に
組み込む際も、UI上の文言や実装コメントでこの区別が曖昧にならないよう注意する。

## 実行方法

```bash
cd programs/syllabus_courses
pip install -r requirements.txt
python scrape.py                  # 既定: 2026年度・全キャンパス・全学部（学部/学科タグなし）
python scrape.py --year 2025      # 年度を変える
python scrape.py --campus 112     # キャンパスコードで絞り込み（112=一部生田 が本プロジェクトの対象キャンパス）
python scrape.py --dept 606100    # 学部・学科コード(crclm)で絞り込み（606100=ネットワーク情報学科）
python scrape.py --by-dept        # 【推奨】departments.json の全学科(33学科)を1つずつ検索し、
                                   # 各科目に所属学部/学科(departments配列)を付与する
```

`--by-dept` は検索結果一覧に学部・学科の列が無いため、学科ごとに絞り込み検索を繰り返すことで
後付けで所属を特定する方式。同じ科目が複数学科のカリキュラムに含まれる場合（教養科目など）は
1件にまとめた上で `departments: [{faculty, department}, ...]` に全ての所属を列挙する
（詳細は下記「出力ファイル」参照）。`index.html` の学部/学科プルダウンはこの `--by-dept` の
出力を前提にしている。

出力先を変えたい場合は `--out-dir <path>` を指定する（既定は `programs/syllabus_courses/output/`）。

途中で落ちた場合は同じコマンドでもう一度実行すれば、`output/.checkpoint.json` を見て
未取得の分（`--by-dept` なら未取得の学科）だけを取りに行く。

## サイトの構造（2026-09時点の調査結果）

- 検索フォームは
  `https://syllabus.acc.senshu-u.ac.jp/syllsenshu/slbssrch.do?clearAccessData=true&contenam=slbssrch&kjnmnNo=12`
  への GET。**ログイン不要**、誰でも閲覧できる。`robots.txt` は存在しない（404）。
- 検索・ページングは同じURLへの POST（JSESSIONID Cookie でセッションを維持する、いわゆる
  Campusmate-J系と思われるJSPベースのシステム）。
- 一覧は1ページ最大200件まで表示件数を変えられる。2026年度・全学部・全キャンパスで検索すると
  総数 9,255件（≒47ページ）で、全件取得しても実際に投げるHTTPリクエストは50件前後で済む。
- ページ番号（pageCount）は連番でアクセスする必要はなく、任意のページへ直接ジャンプできることを
  確認済み。これが再開処理を単純にできている理由。

### クロール時に踏んではいけない罠

検索結果一覧をページングしている途中で、一覧以外のページ（科目の「詳細」ページ `slbssbdr.do` 等）に
寄り道すると、**次のページング要求がサーバ側で「セッションタイムアウト」エラー画面になる**
（サーバがユーザーの画面遷移を厳密にシーケンス管理していて、想定外の遷移をすると壊れるタイプの実装。
ブラウザの戻るボタンで操作すると処理が終わらなくなる、という現象も同じ原因とみられる）。

このスクリプトは**詳細ページには一切アクセスしない**ことでこれを回避している。幸い、詳細ページを
見ても教室情報は載っていない（一覧にもない）ため、寄り道する理由自体がない。

**もう1つの罠（`--by-dept` 実装時に発覚）**: 同じセッション内で「検索→ページング完了」の後、
続けて別の検索条件で新しい検索を投げると、次の検索結果が正しく返らない（総件数の表示が無い
壊れたレスポンスになる）。`clearAccessData=true` 付きの初期ページを**新しい検索の前に毎回
踏み直す**ことで回避している（`run_by_dept` 内の `do_initial_get` 呼び出し）。
また、検索結果0件のときは通常の「X-Y件表示/Z件中」ではなく「検索結果は0件です。」という
専用メッセージになる（これはエラーではなく正常系。実際に2部の休止学科などで発生する）。

## 収集できる項目・できない項目

一覧テーブルの列は「No / 科目名 / 開講期間・曜日・時限 / 担当教員」の4列のみ。

- **教室（location）情報は一覧にも詳細ページにも一切掲載されていない。** そのため `courses.json` の
  `room` は常に `null` になる。
- **学部・学科は一覧に列として出てこない。** `value(crclm)` で学科を指定して絞り込み検索した場合に
  「この検索結果はその学科に属する」と後付けで分かるだけ（`--by-dept` はこれを42学科分繰り返して
  実現している）。
- **学年（対象年次）は一覧テーブルには出てこない。** ただし「配当」欄（例:
  「配当　ネット学科１」= ネットワーク情報学科・1年次）という形で、学部/学科と一緒に
  学年相当の情報が載っている箇所が別にあるらしい（ユーザー確認情報、2026-09-09）。
  今回の調査・`--by-dept` 実装では一覧テーブルの4列（No/科目名/開講期間・曜日・時限/担当教員）
  しか見ておらず、この「配当」欄がどこに出るのか（詳細ページ内か、検索結果の別ビューか）は
  **未確認・今回は対応を見送っている**。次に着手するときは、まず「配当」欄が実際にどのページの
  どの位置に出るかをブラウザで直接確認してから着手すること。もし詳細ページ側にしか出ない場合、
  「クロール時に踏んではいけない罠」（下記）に必ず注意し、一覧のページングとは別セッション・
  別パスで（例: 先に全科目のURLを集めてから、ページング処理を挟まず詳細ページだけを巡回する）
  取得する設計にすること。

## 学期(term)の対応表

サイトの検索フォーム `value(kkikancd)` セレクトから取得した値と、本ツールが出力する `term` の対応:

| サイト上の表記 | サイトの内部コード(kkikancd) | 本ツールの `term` |
|---|---|---|
| 前期 | 1 | `spring` |
| 後期 | 2 | `fall` |
| 通年 | 3 | `spring` と `fall` の**両方**（同じ曜日・時限で2行出力する） |

実際の判定は検索結果一覧の各科目行に書かれている「前期／後期／通年」の文字列（例:
「前期　火曜日　1時限」）から行っている（`kkikancd` は検索の絞り込み条件としてのみ存在し、
一覧のフィルタには使っていない＝毎回全学期分をまとめて取得している）。

## 曜日番号の対応表

`programs/timetables/functions/api/_lib/validate.ts` の `MAX_DAY_OF_WEEK`（0-5=月-土）に合わせている。

| 曜日 | `day_of_week` |
|---|---|
| 月 | 0 |
| 火 | 1 |
| 水 | 2 |
| 木 | 3 |
| 金 | 4 |
| 土 | 5 |
| 日 | 非対応（出現しても出力から除外・stderrにログ） |

`period` は1〜7限のみ対応（`MAX_PERIOD = 7` と同じ）。2026年度の実データでは8限以降の科目は
確認されなかった（`定時外` として別枠になっているとみられる）。

## 既知の制約・スキップした科目

- **「定時外」「集中」など曜日・時限が固定されない開講形式の科目はスキップする**
  （オンデマンド科目、集中講義など）。`day_of_week`/`period` が一意に決まらないため。
  2026年度の全学部・全キャンパス実行では136件がこれに該当し、stderrに件数を出力している。
- 教室（`room`）は常に `null`。シラバスサイトに教室情報が存在しないため。
- 1科目が週に複数コマ（曜日・時限）を持つ場合（ゼミ形式の科目などで
  「月曜4限＋月曜5限」のように `<br>` 区切りで複数掲載されているケース）は、そのコマの数だけ
  複数行として出力する。`timetable_entries` が「1行=1コマ」のスキーマなのでこれに合わせている。
- 完全に同一（科目名・曜日・時限・学期・担当教員が全て一致）の行が重複している場合は
  `courses.json` 生成時に1件にまとめている（同じ科目が複数の学部カリキュラムに
  クロスリストされているケースがあり、生データ `courses_raw.jsonl` には重複が残る）。

## 出力ファイル

- `output/courses.json` — 最終成果物。`--by-dept` で生成した場合は以下の形（`departments` 配列つき）。
  ```json
  {
    "course_name": "アジアの経済１",
    "day_of_week": 2,
    "period": 2,
    "term": "fall",
    "room": null,
    "instructor": "大橋　英夫",
    "departments": [
      { "faculty": "経済学部", "department": "国際経済学科" },
      { "faculty": "経済学部", "department": "現代経済学科" },
      { "faculty": "経済学部", "department": "生活環境経済学科" },
      { "faculty": "経済学部", "department": "経済学科" }
    ]
  }
  ```
  （`--by-dept` を付けない通常実行の場合は `departments` を持たず、`room`/`instructor` 等のみのシンプルな形になる）
- `output/courses_raw.jsonl` — 検索1回（`--by-dept` なら学科1つ）ごとに逐次追記される生データ
  （集約前、1行1JSON）。クラッシュ再開のためのキャッシュも兼ねる。`--by-dept` 実行後に
  `departments` 集約だけをやり直したい場合、この生データから
  `dedupe_and_write_with_departments()`（`scrape.py` 内の関数）を再実行すれば、
  大学サイトに再アクセスせずに `courses.json` だけ作り直せる。
- `output/.checkpoint.json` — 検索条件・モードと取得済みページ/学科の記録。
  検索条件やモードが変わると自動的に最初からやり直す。
- `departments.json` — `value(crclm)` セレクトから抽出した学部→学科の対応表。`--by-dept` が使う。
  年度が変わって学科構成が変わった場合はここを更新する。

## 礼儀正しさ（politeness）について

- User-Agent は `IKU-NAVI-timetables-scraper/1.0` として、プロジェクトの公式紹介ページ
  （<https://project.ne.senshu-u.ac.jp/2026/04/>）のURLを添えて素性を名乗っている。
  個人のメールアドレス等は含めていない。
- 各HTTPリクエストの間に `REQUEST_DELAY_SECONDS`（既定1.0秒）のスリープを入れている。
- 1ページの取得件数をサイトが許す最大値（200件）にすることで、必要なリクエスト数そのものを
  減らしている（全学部・全キャンパスでも約50リクエストで完了する）。
- 詳細ページには一切アクセスしない（上記「クロール時の罠」を参照）。
- 取得結果は都度ディスクに書き出すため、同じページを何度も取り直すことがない。

## 実行結果（2026-09-09 時点）

`python scrape.py --by-dept`（2026年度・全キャンパス・33学科）を実行し、以下の結果を得た。

- 対象学科数: 33学科（`departments.json`。学部ヘッダー自体を除いたリーフ学科の数）
- 収集した「科目×曜日・時限×学科」の生行数: 45,579行
- 学科をまたぐ重複を集約した最終件数: **9,533件**（全学部・全キャンパス一括検索した場合の
  総数と完全一致。集約ロジックの妥当性を確認済み）
- うち複数学科のカリキュラムに属する科目（教養科目など）: 6,411件／単一学科のみ: 3,122件
- スキップ（定時外・集中等で曜日・時限が固定されない科目）: 312件
- 未知の形式・パースエラー: 0件
- 所要リクエスト数: 約280リクエスト（初期GET33 + 検索POST33 + ページング約210）
  ※学科ごとに`clearAccessData=true`を踏み直す必要があるため、単純な全学部一括検索(約49リクエスト)
  より増える。1リクエスト1秒スリープを含め、実行時間は約5分。
- サーバー負荷・エラーについて: 全リクエストで200 OK、レート制限やブロックの兆候なし

## シラバス検索ページ（`index.html`）

大学公式サイトの「戻るボタンで固まる」等の不具合を踏まずに、`courses.json` をオフラインで
検索できる静的ページ。大学サイトには一切アクセスしない。

```bash
cd programs/syllabus_courses
python -m http.server 8000   # このディレクトリで簡易サーバーを立てる
# ブラウザで http://localhost:8000/index.html を開く
```

- 科目名でのインクリメンタル検索
- 右上の「学部」→「学科」プルダウン（カスケード。学部を選ぶとその学部の学科だけに絞られる）で
  科目を絞り込み
- **「学年」プルダウンは今回は実装していない**（今回のスクレイパーは学年に相当するデータを
  収集できていないため。「配当」欄に学年情報がある可能性については上記「収集できる項目・
  できない項目」参照。学年データが必要になったら、そちらを調査した上で改めて対応する）
- 初期状態では何も表示しない（検索語か学部を指定するまで一覧を出さない。9,533件を無条件で
  描画すると重いため）。1回の検索結果は最大500件まで表示し、それ以上は絞り込みを促すメッセージを出す

## timetables アプリへの組み込みについて

`courses.json` は `programs/timetables/scripts/sync-courses.sh` によって
`programs/timetables/public/courses.json` へコピーされ、Viteのビルドでそのまま `dist/` 直下に
含まれる静的アセットとして配信される（D1には取り込んでいない。モノレポの Root directory 制約上
`programs/timetables` から `programs/syllabus_courses` を直接参照できないための静的コピー方式）。
timetables側の `src/course-catalog.ts` がこれを `fetch("/courses.json")` して、科目名オートコンプリート・
曜日/時限の自動入力、および「他の学生が同じ授業に登録した教室を自動入力する」機能（ユーザー設定
`auto_fill_location`、既定オフ）の参考データとして使っている。

シラバスを再スクレイピングした後は、`programs/timetables` で `npm run sync-courses` を実行して
コピーを更新し、差分をコミットする（自動化はしておらず手動運用）。組み込み先のUIでも、このデータが
「開講予定」であって「個人の履修状況」ではないことを誤解を招かない形にしている。
